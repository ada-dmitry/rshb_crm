# CRM возврата покупателей

Этапы 1–9: Rails-каркас с PostgreSQL, входом фермера, моделями покупателей,
заказов и согласий, воспроизводимой демобазой, RFM-панелью, черновиками кампаний
и подтверждаемым ручным запуском локальной симуляции. Есть аналитика на явно
моделируемых событиях доставки и перехода. Реальных рассылок нет.
Покупатели и согласия доступны
только для просмотра.

Стек: **Ruby 4.0.7**, **Rails 8.1.4**, **PostgreSQL 16**, Hotwire (Turbo,
Stimulus и Importmap). Версии зависимостей закреплены в `Gemfile.lock`.
Исходные материалы в `sources/` и Nix-окружение сохранены.

- [Архитектура, соответствие требованиям и ограничения](docs/architecture.md).
- [Пятиминутная демонстрация и браузерная приёмка](docs/demo.md).
- Сквозной HTTP-сценарий: `test/integration/crm_flow_test.rb`.

## Основной запуск: Docker Compose

Нужны Docker Engine и Docker Compose v2. Из корня проекта:

```bash
docker compose up --build -d
docker compose logs -f web
```

Откройте <http://localhost:3000/>. Проверка работоспособности:
<http://localhost:3000/up>. Первый запуск скачивает образы и устанавливает gems.
Compose ждёт healthcheck PostgreSQL; entrypoint выполняет `db:prepare`
перед запуском Rails. Это подготовка/миграция, **не сброс данных**.

Контейнер запускается в `development`, содержит тестовые зависимости и слушает
только `127.0.0.1` хоста. Это локальное демо, не production-deploy.
PostgreSQL не публикует порт на хосте. Копировать исходники в том не нужно;
после изменения кода повторите `docker compose up --build -d`.

В одном из проверенных окружений `docker` заменён на Podman/podman-compose.
Образ, HTTP, тесты и сохранность данных проверены через этот совместимый
runtime, но автоматический healthcheck Podman запускается вне хранилища
Podman и не видит контейнер. Для проверки его запускали вручную командой
`docker healthcheck run rshb_stipa_db_1`; системные настройки не менялись.
`docker compose restart` в podman-compose также дал гонку запуска зависимостей;
после повторного `up -d` данные сохранились. После `down` и нового `up`
сохранность данных тоже подтверждена.
Запуск без ручной помощи на настоящем Docker Compose v2 ещё нужно проверить.
В podman-compose повторный `up --build -d` может оставить web на старом образе.
После сборки обновите только web командой
`docker compose up -d --no-deps --force-recreate web`; том PostgreSQL сохраняется.

`.env` необязателен. При необходимости скопируйте `.env.example` в `.env`
(не перезаписывайте существующий файл) и измените `PORT` или
`POSTGRES_PASSWORD`. Пароль должен состоять из URL-безопасных символов.
Настройки `.env` читает Compose, Rails сам этот файл не загружает.
Примерный пароль предназначен только для локального демо.
Изменение `POSTGRES_PASSWORD` не меняет пароль в уже созданном томе PostgreSQL.

### Проверки

```bash
docker compose config --quiet
curl --fail http://localhost:3000/up
curl --fail http://localhost:3000/
docker compose exec web bin/rails zeitwerk:check
docker compose exec -e RAILS_ENV=test web bin/rails db:prepare
docker compose exec -e RAILS_ENV=test web bin/rails test
```

При другом `PORT` используйте его в URL. В Compose приложение использует
`rshb_stipa_development`, тесты — отдельную `rshb_stipa_test` через
`TEST_DATABASE_URL`. Никогда не направляйте тесты на БД с нужными данными:
Rails может пересоздавать тестовую схему.

### Остановка и сохранность данных

```bash
docker compose restart
docker compose down
docker compose up -d
```

Данные PostgreSQL остаются в именованном томе `postgres_data` (Compose добавляет
префикс проекта). Не меняйте имя проекта/каталога при проверке сохранности.
**Не используйте `docker compose down -v`, `db:reset` или удаление тома**, если
данные нужно сохранить. Перезапуск web повторно вызывает безопасный `db:prepare`.

Проверка данных без добавления бизнес-моделей (временная служебная таблица):

```bash
docker compose exec db psql -U rshb_stipa -d rshb_stipa_development -c "CREATE TABLE foundation_persistence_probe (value text); INSERT INTO foundation_persistence_probe VALUES ('stage-1');"
docker compose down
docker compose up -d
docker compose exec db psql -U rshb_stipa -d rshb_stipa_development -c "SELECT value FROM foundation_persistence_probe;"
docker compose exec db psql -U rshb_stipa -d rshb_stipa_development -c "DROP TABLE foundation_persistence_probe;"
```

Ожидается `stage-1`. Выполняйте только в демобазе и если такого имени таблицы
ещё нет; после успешной проверки удаляется только созданная служебная таблица.

## Разработка с Nix

Существующий flake рассчитан на `x86_64-linux`. Нужны Nix с flakes и direnv:

```bash
direnv allow
# После загрузки окружения direnv (либо внутри nix develop):
db-up
bin/setup --skip-server
bin/rails server
```

`db-up` запускает только проектный PostgreSQL 16, не системный сервис.
`PGHOST` указывает на `tmp/pgsocket`, `PGDATA` — на `tmp/pgdata`.
Gems устанавливаются в `vendor/bundle`; эти каталоги исключены из Git и образа.
`bin/setup` устанавливает gems и выполняет `db:prepare`, не `db:reset`.
Остановка Rails — Ctrl+C, остановка локальной БД — `db-down`.
Не удаляйте `tmp/pgdata`, если нужны локальные данные.

```bash
RAILS_ENV=test bin/rails db:prepare
bin/rails test
bin/rails zeitwerk:check
```

Не запускайте Compose и локальный Rails на одном порту одновременно.

## Обычный локальный запуск без Nix

Установите Ruby 4.0.7, Bundler 4.0.20, PostgreSQL 16 и зависимости для сборки
gems: C/C++-компилятор, make, pkg-config, Git, заголовки libpq и libyaml.
PostgreSQL должен быть запущен; роль должна иметь право создавать БД.
Node.js не требуется для Importmap.

Пример для локальной роли `crm_dev` (заранее создайте её с правом CREATEDB):

```bash
export PGHOST=127.0.0.1
export PGPORT=5432
export PGUSER=crm_dev
# При парольной аутентификации задайте PGPASSWORD безопасным способом.
gem install bundler -v 4.0.20
bin/setup --skip-server
bin/rails server
```

Без `DATABASE_URL` используются `rshb_stipa_development` и `rshb_stipa_test`.
Для внешней БД можно задать `DATABASE_URL` с адресом БД приложения и
`TEST_DATABASE_URL` с адресом **другой** тестовой БД.
Если `TEST_DATABASE_URL` не задан, тесты используют
`postgresql:///rshb_stipa_test` и параметры libpq (`PGHOST`, `PGUSER` и другие),
а не `DATABASE_URL`. Проверки те же, что в разделе Nix, без `db-up`.

## Вход фермера (этап 2)

Стартовая страница `/` и healthcheck `/up` публичны. Кабинет `/crm`
требует входа через `/session/new`. После выхода серверная сессия удаляется.
Регистрации, восстановления пароля по почте и внешней отправки писем нет.

### Подготовка демопользователя

`db:seed` создаёт локального демопользователя `farmer@example.com` с паролем
`local-demo-password`, а также демобазу покупателей. Это публичные тестовые
реквизиты, не используйте их для production или доступного извне приложения.
Обычный повторный запуск приложения не вызывает `db:seed`; при подготовке
пустой БД Rails `db:prepare` может загрузить seeds.

Чтобы задать другой пароль для этой почты **до первой загрузки** или добавить
другого демопользователя, в Bash задайте почту и введите отдельный пароль
скрытым вводом (12–72 **байта**, не используйте личный пароль):

```bash
export DEMO_EMAIL=farmer@example.com
read -r -s -p 'Пароль демопользователя: ' DEMO_PASSWORD
export DEMO_PASSWORD
docker compose exec -e DEMO_EMAIL -e DEMO_PASSWORD web bin/rails db:seed
unset DEMO_PASSWORD DEMO_EMAIL
```

Не указывайте пароль непосредственно в командной строке, Git или `.env.example`.
Переменные передаются только команде подготовки; сохранять их в Compose не нужно.
Для Nix/обычного локального запуска вместо `docker compose exec ...` выполните
`bin/rails db:migrate`, затем `bin/rails db:seed` с теми же переменными.
Демоподготовка разрешена только в `development` и `test`.
Повторная подготовка той же почты сохраняет пароль и сессии, не сбрасывая доступ.
Без переменных используется демопользователь по умолчанию. Переменные создают
указанного пользователя дополнительно к стандартному, если почта отличается.
Для нового пользователя нужны обе переменные; существующий пароль не меняется.

Откройте `/session/new`, введите заданные почту и пароль. После входа
появится кабинет фермера; кнопка «Выйти» снова закроет доступ.
Кабинет показывает обзор базы, покупателей, сегменты, рекомендации и черновики кампаний.

```bash
bin/rails test test/integration/authentication_test.rb test/services/demo/user_seed_test.rb
bin/rails test
bin/rails zeitwerk:check
bin/rubocop
bin/brakeman --no-pager
```

Вход ограничен десятью попытками за три минуты с одного IP.
Ограничитель хранится в памяти одного web-процесса и сбрасывается при его
перезапуске; для нескольких процессов нужен общий store. Это локальное демо,
а не готовая production-аутентификация. Cookie сессии подписана, имеет
`HttpOnly` и `SameSite=Lax`; в production также выставляется `Secure`.

## Покупатели, заказы и согласия (этап 3)

Локальная подготовка (в Nix — после загрузки окружения):

```bash
bin/rails db:migrate
bin/rails db:seed
```

В Compose используйте `docker compose exec web bin/rails db:migrate` и
`docker compose exec web bin/rails db:seed` после пересборки приложения.
Загрузка разрешена только в `development` и `test`, выполняется транзакционно.
Никаких реальных сообщений и сетевых запросов она не выполняет.

На пустой базе создаются **200 покупателей, 1 000 заказов и 400 согласий**
(каналы `email` и `sms`). Все данные синтетические: адреса принадлежат
`example.com`, телефонные контакты имеют намеренно непригодный для отправки
формат `demo-phone-NNN`. Это не реальные номера абонентов.

Данные рассчитаны относительно **13 октября 2026 года, 12:00 UTC**, независимо
от дня загрузки. Есть 20 покупателей без заказов, отсутствующие контакты,
отказы, отменённые заказы, заказы старше года и будущие заказы. Последние
предназначены для проверки исключений при будущей RFM-сегментации.

Правила модели:

- `Customer.external_id` и `Order.external_id` уникальны; email не служит
  идентификатором покупателя и может отсутствовать.
- `Order.total_cents` — целое число копеек RUB (`bigint`), неотрицательное;
  статусы — `completed` и `cancelled`, дата — `ordered_at`.
- На покупателя разрешено одно согласие для каждого канала. `granted`
  по умолчанию `false`; отсутствие записи тоже не означает согласия.
- `Consent.changed_at` хранит дату начального состояния и меняется при
  смене `granted` через модель. Сохранение того же состояния дату не меняет.
  Прямые SQL-обновления обходят callbacks и не предназначены для изменения согласий.
- БД проверяет внешние ключи, уникальность, допустимые статусы/каналы,
  обязательные значения и неотрицательность суммы. Покупателя с заказами
  нельзя удалить через модель; внешний ключ также защищает историю заказов.

Повторная загрузка добавляет только отсутствующие записи по стабильным ключам
`demo-customer-NNN` и `demo-order-NNNN`. Она **не перезаписывает** имена,
контакты, суммы, статусы, согласия или их даты, не удаляет вручную созданные
записи и не меняет пароли/сессии. Если удалить демозапись, последующая загрузка
создаст её заново; это в том числе касается удалённого согласия. Поэтому не
используйте повторную демозагрузку как импорт реальной клиентской базы.

```bash
bin/rails test test/models test/services/demo
bin/rails test
bin/rails zeitwerk:check
bin/rubocop
bin/brakeman --no-pager
```

## RFM-сегментация и рекомендации (этап 4)

`RfmQuery` одним SQL-запросом рассчитывает метрики всех покупателей, включая
покупателей без подходящих заказов. `Segmentation::Rfm` добавляет баллы,
сегмент, объяснение, дату расчёта и длину окна. Расчёты ничего не сохраняют
в БД. Параметры и порядок правил закреплены в `config/segment_rules.yml`.

По умолчанию расчёт выполняется на **13 октября 2026 года**, окно —
**365 календарных дней**, включая день расчёта. Время всегда UTC:
`[2025-10-14 00:00:00, 2026-10-14 00:00:00)`. В расчёт попадают только
заказы `completed` внутри окна. Отменённые, более ранние и будущие заказы
исключены. «Будущий» означает следующий календарный день и позднее,
поскольку расчёт за выбранную дату охватывает весь день.

- **R** — число календарных дней от последней подходящей покупки до даты расчёта.
- **F** — количество подходящих заказов.
- **M** — их суммарная стоимость в целых копейках RUB.
- Если в окне нет завершённых заказов: R отсутствует, F/M и баллы равны нулю,
  сегмент `no_purchases`. Это **не утверждение**, что покупатель никогда не покупал.

Баллы — фиксированные, не квантили текущей базы:

| Балл | R (дни) | F (заказы) | M (копейки RUB) |
|---|---|---|---|
| 3 | 0–30 | 5 и более | 100 000 и более |
| 2 | 31–90 | 2–4 | 30 000–99 999 |
| 1 | 91 и более | 1 | 0–29 999 |

Первое совпавшее правило определяет сегмент:

| Приоритет | Сегмент | Условия по баллам |
|---|---|---|
| 1 | `champions` — лучшие покупатели | R ≥ 3, F ≥ 3, M ≥ 3 |
| 2 | `loyal` — постоянные покупатели | R ≥ 2, F ≥ 3 |
| 3 | `at_risk` — риск ухода | R ≤ 1, F ≥ 2 |
| 4 | `sleeping` — давно не покупали | R ≤ 1 |
| 5 | `new_customers` — одна недавняя покупка | R ≥ 3, F ≤ 1 |
| 6 | `active` — остальные покупатели с покупками | Резервное правило |

`no_purchases` обрабатывается до этой таблицы. Название `new_customers`
означает одну недавнюю покупку **в окне**, а не доказанную новизну клиента.
Пороги — демонстрационные допущения, не проверенная маркетинговая модель
и не прогноз отклика или роста выручки.

`Recommendations::ForSegment.call(segment)` возвращает идеи повторной покупки,
сезонного предзаказа, дополнительного товара или знакомства с ассортиментом.
У каждой идеи есть причина, предлагаемый канал `email`, условное время и
`requires_confirmation: true`. Товары, наличие, любимые позиции и сроки
поставки не выдумываются: их должен уточнить фермер.

**Сегмент не даёт разрешения на сообщение.** Здесь согласия, контакты и лимиты
не фильтруются; это отдельная логика следующих этапов. Идеи не создают кампаний
и ничего не отправляют.

Пример read-only расчёта после загрузки демобазы:

```bash
bin/rails runner 'puts Segmentation::Rfm.call.group_by(&:segment).transform_values(&:size)'
bin/rails runner 'result = Segmentation::Rfm.call.first; puts result.explanation; puts Recommendations::ForSegment.call(result.segment).map(&:title)'
bin/rails test test/queries/rfm_query_test.rb test/services/segmentation test/services/recommendations
```

Для другой даты/окна: `Segmentation::Rfm.call(as_of: "2026-10-14", window_days: 30)`.
Дата — `Date` или ISO-строка, длина окна — целое число от 1 до 3650 дней.
Прямой вызов `RfmQuery.call` требует явно указать `as_of`.

## CRM-панель (этап 5)

Все страницы требуют входа фермера:

- `/crm` — обзор базы: число покупателей, **все** заказы за всё время,
  сумма только завершённых покупок в окне RFM и семь карточек сегментов.
- `/crm/customers` — список, поиск и фильтр по сегменту. Поиск по имени,
  внешнему ID, email или телефону не зависит от регистра; `%` и `_`
  воспринимаются буквально. Запрос ограничен 100 символами.
- `/crm/customers/:id` — контакты, показатели RFM и объяснение сегмента,
  согласия по каждому каналу и полная история заказов, включая не вошедшие в RFM.
- `/crm/segments/:id` — причина сегмента, количество покупателей, идеи действий
  и переход к списку покупателей выбранного сегмента.

Списки покупателей и заказов разбиты по 20 записей. Покупатели упорядочены
по ID, заказы — от новых к старым (при одинаковой дате — по ID). Пагинация
сохраняет поиск/сегмент. Некорректная страница заменяется первой, слишком
большая — последней. Неизвестный покупатель или сегмент возвращает 404.

Пустой поиск, пустой сегмент, пустая база и отсутствие заказов обозначены явно.
Отсутствующее согласие не отображается как разрешение. Просмотр страниц не
меняет бизнес-данные. В шапке показан демонстрационный характер данных;
дата и окно анализа видны на каждой CRM-странице.

Из карточки сегмента и каждой идеи можно перейти к созданию черновика
с предвыбранным сегментом/поводом. Безопасный предварительный охват
после исключений рассчитывается в карточке кампании (этап 6).

На мобильном экране карточки складываются в одну колонку, меню и формы
переносятся. Таблицы прокручиваются **внутри собственной области**, не создавая
горизонтальную прокрутку всей страницы. Доступны подписи полей, таблиц,
видимый keyboard-focus и ссылка перехода к основному содержимому.

```bash
bin/rails test test/integration/crm_navigation_test.rb
PARALLEL_WORKERS=2 bin/rails test
```

Проверка Playwright выполнена при 390 и 1440 px: вход, обзор, поиск,
фильтрация, пагинация, карточки, пустые состояния. На обеих ширинах
горизонтального переполнения страницы нет; ошибок браузерной консоли не обнаружено.

## Черновики кампаний и предварительный охват (этап 6)

После обновления приложения выполните `bin/rails db:migrate` (в Compose —
`docker compose exec web bin/rails db:migrate` после пересборки web).

- `/crm/campaigns` — сохранённые кампании, по 20 записей, новые первыми.
- `/crm/campaigns/new` — конструктор: название, сегмент, повод, текст до
  2 000 символов, канал Email/SMS, планируемое время, дата и окно RFM.
- `/crm/campaigns/:id/edit` — изменение черновика с повторным расчётом после сохранения.
- `/crm/campaigns/:id` — текст, параметры и предварительный охват.
- `/crm/campaigns/:id/preview` — свежий пересчёт **без записи** в БД.

Все страницы и сохранение требуют входа. Создатель фиксируется из текущей
серверной сессии; `user_id`, статус и любые поля подтверждения не принимаются
из формы. Это одно общее хозяйство, **не** многопользовательская изоляция:
все допущенные пользователи работают с общей базой и общими черновиками.

Дата и окно RFM сохраняются в кампании и определяют кандидатов сегмента.
Контакты, согласия и история проверяются заново при каждом preview,
включая повторный вызов с ранее загруженным объектом покупателя.
Подходящий сегмент не означает разрешения на контакт:

| Код исключения | Причина |
|---|---|
| `missing_contact` | Нет контакта для выбранного канала |
| `invalid_contact` | Некорректный email или SMS-номер не в формате E.164 |
| `missing_consent` | Запись согласия по этому каналу отсутствует |
| `refused` | По этому каналу явно нет согласия |
| `frequency_limit` | Есть слишком недавний контакт по любому каналу либо будущая история контакта |

Для SMS требуется `+` и 8–15 цифр, первая цифра не ноль. Синтетические
`demo-phone-NNN` намеренно не проходят проверку. Согласие Email не заменяет
согласие SMS. Показаны **все** применимые причины, а не только первая.

Частотный лимит — **один контакт за 7 × 24 часа по всем каналам**. Он проверяется
относительно **планируемого времени кампании**, которое всегда вводится и
разбирается в UTC, независимо от timezone браузера/приложения. Контакт ровно
семь дней назад уже не блокирует; на микросекунду новее — блокирует.
Будущая запись в истории исключает контакт консервативно. Статусы
`pending`/`failed` без `contacted_at` не расходуют лимит.

`CampaignRecipient` — основа истории контактов для следующего этапа:
уникальность пары кампания/покупатель, снимок канала, статус и время контакта.
`simulated` требует время, другие статусы — его отсутствие. Preview **не создаёт**
таких записей, не резервирует лимит и не фиксирует будущих получателей.

Охват — число допустимых кандидатов по текущим данным, не прогноз доставки,
покупок или выручки. Если согласие отозвано или история изменилась после
расчёта, цифры устаревают. Запуск повторяет проверки и требует подтверждения
фермера (этап 7 ниже). Фонового планировщика нет, а дата в форме ничего
не отправляет. Нулевой охват и пустой сегмент показаны явно.

```bash
bin/rails test test/models/campaign_test.rb test/models/campaign_recipient_test.rb
bin/rails test test/services/campaigns test/integration/campaigns_test.rb
PARALLEL_WORKERS=2 bin/rails test
```

и нулевой SMS-охват. На исходной демобазе для `champions` с датой RFM

## Подтверждение и локальная симуляция (этап 7)

После обновления выполните `bin/rails db:migrate`, без сброса данных.

1. Сохраните черновик и проверьте текст, предложение, канал, время и RFM.
2. Нажмите «Подтверждаю текущую версию черновика». `POST /crm/campaigns/:id/confirm`
   принимает версию показанного черновика. Пользователь и время подтверждения
   берутся только из серверной сессии и часов сервера. Устаревшая версия — HTTP 409.
3. Любое изменение параметров сбрасывает подтверждение. Формы редактирования
   используют optimistic locking: устаревшая форма не перезапишет новую версию.
4. После наступления выбранного времени вручную нажмите «Запустить локальную
   симуляцию» (`POST /crm/campaigns/:id/launch`). Без подтверждения или раньше
   `scheduled_at` сервер возвращает HTTP 422 без создания получателей.

При запуске перечитываются сохранённые параметры кампании и заново определяются
кандидаты RFM по актуальным заказам. Контакты, согласия и история контактов
читаются заново, без SQL-кэша. В отличие от preview, eligibility и лимит
оцениваются на **фактическое серверное время запуска**, а не `scheduled_at`.
Граница лимита — ровно 7 × 24 часа, общий бюджет Email/SMS; точная граница допустима.

Все запуски одного хозяйства сериализованы общей транзакционной PostgreSQL
advisory-блокировкой, взятой до блокировки кампании и проверки eligibility.
Поэтому два запроса одной кампании идемпотентны, а разные кампании не обходят
общий лимит. Это сознательное ограничение пропускной способности MVP:
даже кампании без общих покупателей ждут друг друга. Все пути запуска должны
использовать `Campaigns::Launch`; прямой SQL и ручная запись истории не являются
поддерживаемым способом отправки.

В одной транзакции сохраняются все кандидаты: снимки имени, внешнего ID,
контакта и канала; допустимым — `simulated` и время локального контакта,
исключённым — `excluded`, все коды причин и отсутствие времени контакта.
`excluded` не расходует лимит. Любая ошибка симуляции откатывает весь запуск,
включая уже созданные записи; подтверждение сохраняется для повторной попытки.
Нулевой охват и пустой сегмент тоже завершаются с зафиксированным результатом.

Карточка запущенной кампании и старый URL `/preview` показывают **сохранённый
результат**, а не пересчёт. Изменения покупателя или согласия его не меняют.
Запущенная кампания не редактируется через модель и HTTP (409); повторный запуск
возвращает тот же результат. GET-запросы не подтверждают и не запускают кампанию.

PostgreSQL-триггеры дополнительно запрещают изменение/удаление запущенной кампании
и её получателей, а также добавление новых получателей после запуска. Они защищают
историю даже от методов Rails, пропускающих валидации (`update_columns`, `delete`).
Изменение параметров черновика любым способом сбрасывает подтверждение и повышает
версию. Поэтому схема теперь хранится в **`db/structure.sql`**, а не `db/schema.rb`:
так триггеры сохраняются при подготовке чистой/параллельной тестовой БД. Для
`db:prepare`/дампа нужны `psql` и `pg_dump` (есть в Nix и добавлены в Dockerfile).

Симуляция — только запись в локальную БД. Сетевых адаптеров, сообщений и фоновых
заданий нет. Этап 8 ниже добавляет только моделируемые события и их аналитику.

```bash
direnv exec . bin/rails test test/services/campaigns test/integration/campaign_launch_test.rb test/integration/campaigns_test.rb
direnv exec . env PARALLEL_WORKERS=2 bin/rails test
direnv exec . bin/rubocop
direnv exec . bin/rails zeitwerk:check
direnv exec . bin/brakeman --no-pager
```

Конкурентные тесты используют отдельные соединения и реально пересекающиеся
транзакции: первый запуск удерживается внутри симуляции, второй проверяется
как ожидающий advisory-блокировку в `pg_locks`. Покрыты одна кампания и две
кампании с общим покупателем по разным каналам.

Playwright на 1440 и 390 px: создание → подтверждение → ручной запуск →
фиксированный результат; ранняя кнопка заблокирована, редактирование сбрасывает
подтверждение, повторный POST не меняет результат, редактирование запущенной
кампании даёт 409. Проверены нулевой охват, пустой сегмент, пагинация и старый
URL `/preview`. Переполнения страницы и ошибок консоли нет. В локальной
development-базе оставлены три тестовые кампании: `Этап 7 · браузер 1440`
(24 кандидата / 14 симуляций / 10 исключений), `Этап 7 · браузер 390`
(24 / 0 / 24 после первого контакта) и `Этап 7 · пустой сегмент` (0 / 0 / 0).
Предыдущие данные не сбрасывались. Это результаты локальной симуляции, не доставки.

## Моделируемые события и аналитика (этап 8)

Примените `bin/rails db:migrate` (в Compose — после обновления образа). Миграция
добавляет события, не меняет существующие кампании, согласия или историю контактов.

После нового запуска события моделируются **в той же транзакции**, что получатели
и статус кампании: ошибка откатывает весь запуск. У ранее запущенных кампаний
GET карточки/`preview` ничего не генерирует. Нажмите «Смоделировать события (v1)»
в блоке «Моделируемая аналитика» — это авторизованный
`POST /crm/campaigns/:id/simulate_events`. Для черновика — HTTP 422. Повторное
нажатие не меняет события, контакты, подтверждение или статус кампании.

`CampaignEvent` привязан к зафиксированному получателю. Допустимы только:

- `delivered` — **моделируемая**, а не подтверждённая внешним сервисом доставка;
- `clicked` — **моделируемый**, а не зафиксированный браузером покупателя переход.

Источник всегда `simulated`, версия алгоритма — `1`. События допускаются только
для `simulated`-контактов запущенной кампании; исключённые, `pending` и `failed`
не участвуют. Уникальный индекс получатель/тип, блокировка кампании и транзакция
защищают от дублей и конкурирующих повторов. PostgreSQL дополнительно запрещает
изменение/удаление событий, реальный источник и некорректную хронологию: событие
не раньше контакта, переход — только после моделируемой доставки. Эти ограничения
включены в `db/structure.sql`.

### Воспроизводимость, не прогноз

Алгоритм v1 не использует `Random`, системное время, актуальные заказы или
изменяемые контакты. Для каждой цели берутся первые 16 hex-символов SHA-256 строки
`crm-events-v1:<campaign_id>:<customer_external_id>:<purpose>`; если у старой
истории нет снимка external ID, используется `customer-<customer_id>`.

- Для `delivery`: остаток от деления на 100 меньше 90 выбирает доставку.
- Для `click`: остаток меньше 30 выбирает переход **только при доставке**.
- `delivery_delay`: `30 + остаток по 271` секунд после контакта.
- `click_delay`: `300 + остаток по 3301` секунд после моделируемой доставки.

Это произвольные демонстрационные пороги, **не обещанные 90% доставки или 30%
переходов** и не оценка поведения покупателей. Реальные доли конкретной выборки
могут отличаться. Время событий тоже искусственное и может оказаться в будущем.
События не меняют частотный лимит — его расходует только локальный контакт этапа 7.

### Показатели

Все значения относятся ко всей кампании, независимо от страницы списка получателей.
Считаются уникальные ID получателей через `COUNT(DISTINCT ...)`, а не строки JOIN:

| Показатель | Определение |
|---|---|
| Локальные контакты | Получатели со статусом `simulated` |
| Моделируемые доставки | Контакты с событием `delivered` |
| Моделируемые переходы | Контакты с событием `clicked` |
| Доля доставок | Уникальные доставки / локальные контакты × 100% |
| Доля переходов | Уникальные переходы / уникальные доставки × 100% |

Проценты округляются до одного десятичного знака. При нулевом знаменателе — `—`,
не `NaN`, бесконечность или выдуманный процент. Без сохранённых событий счётчики
равны нулю, но UI отдельно объясняет, что моделирование могло ещё не запускаться
либо модель не выбрала ни одной доставки. При нулевом охвате событий не будет.

Показатели не зависят от текущих контактов, согласий или заказов. Атрибуции
выручки, заявлений о росте продаж, tracking pixel, настоящих click URL, внешних
адаптеров и фонового планировщика нет.

```bash
direnv exec . bin/rails test test/models/campaign_event_test.rb test/services/campaigns/event_simulator_test.rb test/services/campaigns/event_simulator_concurrency_test.rb test/queries/campaign_metrics_query_test.rb test/integration/campaign_analytics_test.rb
direnv exec . env PARALLEL_WORKERS=2 bin/rails test

direnv exec . bin/rails zeitwerk:check
direnv exec . bin/brakeman --no-pager
```

## Изолированная приёмка (этап 9)

Не используйте существующий проект Compose для чистого запуска. Сначала
убедитесь, что имя проекта, том и порт свободны (`docker ps -a`,
`docker volume ls`). Пример для **нового** проекта; если он уже существует,
выберите другое имя, а не удаляйте чужие контейнеры или том:

```bash
export COMPOSE_PROJECT_NAME=crm_acceptance_09
export PORT=3109
docker compose config --quiet
docker compose up --build -d
curl --fail http://localhost:3109/up
docker compose exec web bin/rails zeitwerk:check
docker compose exec -e RAILS_ENV=test web bin/rails db:prepare
docker compose exec -e RAILS_ENV=test -e PARALLEL_WORKERS=2 web bin/rails test
```

Это отдельная сеть и том `crm_acceptance_09_postgres_data`, отдельный сервер
PostgreSQL без порта на хосте. Одинаковое имя БД внутри разных серверов не означает
общие данные. Не задавайте `DATABASE_URL`/`TEST_DATABASE_URL` на существующую БД.
Подготовка новой БД загружает 200 покупателей, 1 000 заказов и демопользователя;
локальная Nix development-база и прежний том не используются.

Публичные реквизиты: `farmer@example.com` / `local-demo-password`.
Пройдите [демонстрацию](docs/demo.md) на <http://localhost:3109/>.
После создания кампании сравните **полный снимок бизнес-таблиц**, а не только
количество записей, до и после перезапуска (в Bash):

```bash
acceptance_snapshot() {
  docker compose exec -T web bin/rails runner 'require "digest"; models = [User, Session, Customer, Order, Consent, Campaign, CampaignRecipient, CampaignEvent]; data = models.map { |m| [m.name, m.order(:id).map(&:attributes)] }; puts "ACCEPTANCE_SHA256=#{Digest::SHA256.hexdigest(data.to_json)}"' | grep '^ACCEPTANCE_SHA256='
}
before=$(acceptance_snapshot) && test -n "$before"
docker compose restart
curl --fail --retry 20 --retry-all-errors --retry-delay 2 http://localhost:3109/up
after=$(acceptance_snapshot) && test "$before" = "$after"
```

Не открывайте браузер между снимками: вход меняет таблицу сессий.
Повторите сравнение с `docker compose down` и `docker compose up -d` вместо
`restart` для проверки пересоздания контейнеров с тем же томом.
В Podman при уже описанной гонке сначала вручную выполните
`docker healthcheck run crm_acceptance_09_db_1`, затем `docker compose up -d`;
не выдавайте восстановление таким способом за беспроблемный Docker Compose.
Завершите только приёмочный проект: `docker compose down` **без `-v`**.
Том остаётся для повторной демонстрации. После пересоздания web-контейнера
в development может потребоваться повторный вход (cookie не считается
гарантированно переносимой между контейнерами); данные кампаний сохраняются.
`unset COMPOSE_PROJECT_NAME PORT`
возвращает терминал к настройкам по умолчанию.
