# Архитектура CRM возврата покупателей

## Назначение и границы

Локальный конкурсный MVP для одного хозяйства: фермер исследует синтетическую
базу, выбирает сегмент и вручную запускает подтверждённую **локальную модель**
коммуникации. Рекомендации объяснимы правилами, а не ML. Доставки и переходы
не получены от клиентов или внешних сервисов и не доказывают рост продаж.

Ruby 4.0.7 / Rails 8.1.4, PostgreSQL 16; серверный HTML, Turbo, Stimulus,
Importmap. Отдельный frontend/build на Node не требуется. Compose запускает
один web-процесс и БД с именованным томом; entrypoint делает `db:prepare`,
не сброс. Nix — альтернативное окружение разработки, не требование для демо.

## Компоненты и поток данных

```text
Браузер → Rails controllers + ERB/Hotwire → PostgreSQL
                   │
                   ├─ RfmQuery → Segmentation::Rfm → Recommendations::ForSegment
                   ├─ Campaigns::Preview → Eligibility (только чтение)
                   └─ Campaigns::Launch (транзакция + общая advisory-блокировка)
                          ├─ новый RFM + Eligibility
                          ├─ снимки CampaignRecipient + SimulatedDelivery
                          ├─ status=launched
                          └─ EventSimulator → CampaignEvent
                                      ↓
                             CampaignMetricsQuery → карточка кампании
```

`Authentication` защищает `/crm/**` серверной сессией; публичны `/`, `/up`
и форма входа. `Current.user` определяет создателя и подтверждающего, не поля
запроса. Cookie подписана, HttpOnly, SameSite=Lax. CSRF-защита Rails включена.
Регистрации и восстановления доступа нет. Несколько допущенных пользователей
видят одно хозяйство: принадлежность кампании автору — не tenant isolation.

## Модель хранения

| Сущность | Связи и смысл |
|---|---|
| `User`, `Session` | Пароль BCrypt; серверные сессии, выход удаляет сессию |
| `Customer` | Стабильный уникальный external ID; контакты могут отсутствовать |
| `Order` | Принадлежит покупателю; целые копейки RUB, completed/cancelled |
| `Consent` | Одно согласие на покупателя/канал email или sms; отсутствие = не разрешено |
| `Campaign` | Автор, параметры RFM, предложение, текст, канал, время UTC, версия, подтверждение и запуск |
| `CampaignRecipient` | Уникальная пара кампания/покупатель; снимки имени/ID/контакта/канала, статус, причины, время контакта |
| `CampaignEvent` | Получатель, тип delivered/clicked, source=simulated, simulation_version=1, искусственное время |

FK, уникальные индексы и CHECK дополняют проверки Rails. Схема хранится
в `db/structure.sql`: PostgreSQL-триггеры запрещают изменение и удаление
запущенных кампаний, их получателей и событий, а также добавление получателей
после запуска. Поэтому при подготовке БД нужны `psql` и `pg_dump`.
Событие допустимо только для simulated-получателя запущенной кампании;
переход требует моделируемую доставку и корректный порядок времени.

Seeds недеструктивны: добавляют недостающие записи по стабильным ключам,
не обновляют существующие контакты/согласия/заказы/пароли. На чистой БД:
200 покупателей, 1 000 заказов, 400 согласий. Демотелефоны намеренно непригодны
для отправки. Базовая дата — 13.10.2026, не текущие часы сервера.

## Сегментация и рекомендации

`RfmQuery` агрегирует завершённые заказы в календарном окне UTC; отменённые,
старые и будущие заказы не входят. `Segmentation::Rfm` применяет фиксированные
пороги и приоритеты из `config/segment_rules.yml`, ничего не записывая в БД.
По умолчанию дата 13.10.2026, окно 365 дней. R — дни с последней покупки,
F — число заказов, M — сумма в копейках. Без подходящих покупок — no_purchases.
Остальные сегменты: champions, loyal, at_risk, sleeping, new_customers, active.
Точные пороги и порядок опубликованы в README и YAML, покрыты граничными тестами.

Рекомендации предлагают повторную покупку, предзаказ, дополнительный товар или
знакомство с ассортиментом, объясняют причину, канал и условное время.
Они не подтверждают наличие/цену/предпочтения: факты уточняет фермер.

## Жизненный цикл и защита повторов

1. **Черновик:** изменяемые параметры, preview без записи получателей и событий.
   Eligibility показывает все причины исключения: missing_contact,
   invalid_contact, missing_consent, refused, frequency_limit.
2. **Подтверждение текущей версии:** POST с `lock_version`, личность и время
   берутся на сервере. Изменение параметров сбрасывает подтверждение;
   устаревшее подтверждение/редактирование получает 409.
3. **Ручной запуск:** без подтверждения или до scheduled_at — 422.
   Фонового планировщика нет. Сегмент и eligibility вычисляются снова;
   preview использует scheduled_at, запуск — фактическое серверное время.
4. **Атомарная фиксация:** общая транзакционная advisory-блокировка всех запусков
   хозяйства, затем блокировка кампании и перечитывание данных. Это сериализует
   разные каналы и кампании, защищая бюджет одного контакта за **7 × 24 часа**.
   Ровно семь дней допустимы, будущая история блокирует. Исключённые без контакта
   бюджет не расходуют. Блокировка снижает пропускную способность сознательно.
5. **Результат:** все кандидаты фиксируются, включая исключённых. Локальные
   контакты, статус launched и события сохраняются в одной транзакции;
   ошибка откатывает весь запуск. Повтор запуска возвращает прежний результат.
   GET карточки и старый `/preview` показывают снимки, не актуальные контакты.
   Редактирование запущенного через HTTP возвращает 409, БД также защищает историю.

`Campaigns::Launch` — единственный поддерживаемый путь запуска. Прямая запись
SQL не является альтернативным каналом отправки. События старых запусков
создаются только отдельным авторизованным POST `simulate_events`, не GET.
Уникальный индекс получатель/тип и блокировка кампании делают его повторяемым.

## Аналитика — исключительно воспроизводимая модель

Алгоритм v1 использует SHA-256 от ID кампании, снимка external ID покупателя
и назначения события. Демопороги 90/30 и искусственные задержки заданы в коде,
не являются прогнозом. Время событий может быть в будущем. Подробная формула
описана в README; повтор не зависит от случайности или текущих контактов.

`CampaignMetricsQuery` одним SQL считает уникальных получателей всей кампании:
доставки / локальные контакты и переходы / доставки. Нулевой знаменатель — `—`.
События не расходуют частотный бюджет. Нет выручки, атрибуции или реального tracking.

`tasks.md`, названный в плане, отсутствует в текущем checkout. Матрица ниже
предварительно сверена с сохранённым `sources/tasks-ui.json`, направление

Это не утверждение о сверке с отсутствующим файлом или свежей редакцией конкурса.

| Требование сохранённого задания | Реализация / доказательство |
|---|---|
| Сегменты и предложения, каналы и время | Карточка `/crm/segments/:id`, YAML правил, Recommendations::ForSegment |
| RFM | RfmQuery + Segmentation::Rfm; тесты границ, окна и исключений заказов |
| Согласия и исключение отказавшихся | Consent + Eligibility; причины видны в preview и снимках |
| Ограничение частоты | Общий лимит Email/SMS, advisory lock; конкурентные тесты реальных транзакций |
| CRM-панель и рекомендации действий | `/crm`, список/карточка покупателя, карточка сегмента |
| Конструктор и прогноз охвата | Черновик + preview; это допустимый охват, не прогноз продаж |
| Только после подтверждения | Версионное подтверждение + ручной POST запуска, сброс при изменениях |
| Аналитика результата | Уникальные показатели **моделируемых** событий; не внешняя доставка |

Сквозное покрытие: `test/integration/crm_flow_test.rb` проходит настоящий POST
входа, сегмент, форму, сохранение, preview, подтверждение, отзыв согласия,
запуск, снимки, аналитику, повторы, запрет редактирования и выход.
Браузерная приёмка и её ограничения описаны в [demo.md](demo.md).

## Ограничения и дальнейшие ручные проверки

- Нет реальных отправок, банковских интеграций, ML, мультитенантности, регистрации,
  импорта, фонового планировщика и production-deploy.
- Покупатели, заказы и согласия в UI доступны только для чтения; отзыв согласия
  в integration-тесте моделируется напрямую через модель.
- Локальный rate-limit входа хранится в памяти одного процесса. Публичные
  демореквизиты и development-режим не подходят для внешнего сервиса.
- После пересоздания development web-контейнера может потребоваться повторный
  вход. При приёмке PostgreSQL-данные и результаты кампаний сохранились полностью.
- Проверен совместимый Podman, **не настоящий Docker Engine / Compose v2**.
  Автоматическое ожидание healthcheck и беспроблемный restart Docker требуют
  отдельной проверки; системные настройки для обхода проблемы не менялись.
- Нужна окончательная сверка матрицы с оригинальным `tasks.md`, если он доступен.
